1. THE PARTS OF AN ENTRY

  - title: "E. Amélineau, *Œuvres de Schenoudi*, 1907 ff"
    description:
      - "Amélineau, E. (1907). *[Œuvres de Schenoudi …](https://…)*. Tome 1. Paris: E. Leroux."
    variants:
      - "A"
    postfixes:
      …
    prefixes:
      …

- title: The name of the source, shown in the first line of the tooltip, after the abbreviation (as in "A: E. Amélineau, Œuvres de Schenoudi …"). In Section 1, this is Crum's own wording.
- description: A list of lines, shown as a bulleted list under the title. This is typically a full bibliographic reference, with a link to a scan where one is available. It may also contain notes for the reader, such as where a manuscript is kept today.
- variants: The abbreviations that Crum uses to cite the source (see below).
- postfixes and prefixes (optional): See below.

title, description, and variants are required. title and description may be left empty, but variants must have at least one item. An entry with neither a title nor a description gets no tooltip at all.
2. VARIANTS

A citation in Crum's text is recognized as a citation of an entry only if it matches one of the entry's variants EXACTLY, including capitalization. If Crum cites a source inconsistently, list every form he uses.

The only exception is spacing. Where Crum is inconsistent in spacing, store the form WITH spaces, and the other spacings are generated automatically. For example, storing 'Cai Copt Mus' as a variant results in the following
variants for the entry:
- 'Cai Copt Mus'
- 'CaiCopt Mus'
- 'Cai CoptMus'
- 'CaiCoptMus'
Storing both 'Cai Copt Mus' and 'CaiCoptMus' would be considered an error, because the former implicitly includes the latter, and redundancy is forbidden.

Every abbreviation must belong to ONE entry only. The same variant (or the same variant with the same prefix or postfix) may not appear in two entries.

Variants also compete with the other abbreviations that we recognize in Crum's text, such as the books of the Bible, and the annotations (see below). Where the same text could be read as more than one of them, the LONGEST abbreviation that fits wins. So a variant that is too short or too common can steal citations that belong to something else. If you suspect a conflict, leave a NOTE explaining it, and we will sort it out.
3. POSTFIXES AND PREFIXES

A postfix is a part of the abbreviation that follows the variant and makes it more specific, often by naming a place, a department, or a part of the work. A prefix is the same, but it precedes the variant. For example, the 'Or' of 'BM Or' (British Museum, Oriental) is a postfix, and the 'P' of 'P Cai Copt Mus' (papyrus) is a prefix.

A citation can bear one prefix, one postfix, or one of each, as in 'OstrLouvre SN'. Spacing works as it does for variants, so the postfix 'Or' of 'BM' covers both 'BM Or' and 'BMOr'.

Postfixes are NOT the numbers that locate a passage within a source (page, column, line, etc.). Those are recognized automatically, and should not be listed here. A number belongs here only if it names a distinct source, as the '1' and '2' of 'Mani 1' and 'Mani 2' do.

Each postfix or prefix is written as key: value, where the value says what the tooltip shows for it. The value can be one of the following:

    postfixes:
      Or: "Oriental" # 1. Text, written like the title.
      K: # 2. Empty. The tooltip shows nothing for it.
      BM: !reference # 3. The tooltip of the entry that 'BM' cites.
    prefixes:
      Ostr: !annotation # 4. The meaning of the annotation 'Ostr'.

1. Text: Shown in the tooltip after the postfix, as in "Or: Oriental".
2. Empty: Used when the postfix needs no explanation, or when its explanation lives in the entry's description (see the NOTE on consolidated postfixes below). Also used as a placeholder for explanations that are still missing.
3. !reference: Used when the postfix or prefix is ITSELF an abbreviation of another source in this file. For example, Crum cites Shenoute's works by the edition or the collection that holds them, as in 'Sh BM' (Shenoute, in the British Museum manuscripts). BM: !reference makes the tooltip show the whole entry of 'BM', so we don't have to write it twice. The key must exactly match an abbreviation of another entry.
4. !annotation: Used when the postfix or prefix is a general abbreviation, rather than a source, such as 'Ostr' (ostracon), 'P' or 'Pap' (papyrus), 'MS' (manuscript), or 'Lect' (lectionary). Our website already knows the meanings of these, so we don't have to write them again. If you are unsure whether an abbreviation is known to us, write its meaning as text, and we will convert it.

Neither !reference nor !annotation takes a value: write nothing after it on the same line, except perhaps a comment.
4. FORMATTING

This file is written in YAML. For more information about YAML syntax, see https://learnxinyminutes.com/yaml/ (a short introduction) or https://yaml.org/spec/1.2.2/ (the full specification).

1. Use consistent indentation.
2. title is a single value. The data can follow on the same line.
3. description is a list. The description: key must reside on its own line, and each item in the description must follow on a line starting with - (a hyphen followed by a space).
4. Use Markdown syntax, specifically:

   - Single asterisks for work titles (typically italicized):
       *title*
     This is used for the titles of works, which are the bulk of the bibliography.

   - Single underscores for other italicized text:
       _italicized_
     This is used for italicized text that is not part of a work title, particularly Latin words such as _penes_, _olim penes_, etc.

   - Double asterisks for clues:
       **clue**
     This is used for tokens that are part of the citation location, in particular volume numbers and postfixes. This helps the user locate citations more quickly in the description.

   - Double underscores for dialects:
       __S__, __B__, etc.
     This is used where the text names the dialect of the manuscript it describes, be it in a title, or in a consolidated postfix whose siglum is a dialect (see the NOTE on postfixes below).

     Crum's text doesn't use boldface, so we've conveniently repurposed both of markdown's strong delimiters, giving each a meaning of its own.

   - The bracket notation for hyperlinks:
       [name](https://example.com/)

   Each value must be a single paragraph, optionally followed by a nested list (see rule 7). Don't separate paragraphs with blank lines.
5. Double-quote all values, except the !reference and !annotation tags.
6. Don't double-quote any keys (such as title, description, etc., and postfix and prefix keys).
7. If a description entry needs to contain a list nested within it, then do
   the following:
   - Write description: on a separate line.
   - Begin the entry with - |- (a hyphen and a space, followed by a vertical bar and a hyphen).
   - The description can follow afterwards, on the next indented lines, and it should NOT be surrounded by double quotes.
   - Use Markdown notation for lists. Each item should be preceded by - .
For all of the above, see examples throughout the file.
5. CONVENTIONS
NOTE: (#671) CONSOLIDATED POSTFIXES. Crum often repeats only the postfix of a citation in the _ibidem_ that follows it ('ManiP …, ib K …'), and a bare postfix is not a parsable key. Where an entry's postfixes merely name parts of one work, we therefore CONSOLIDATE it: each postfix description moves into the entry's own description, introduced by its own siglum (**K**: … as a clue, or __F__: … where the postfix names a dialect), and the postfixes key is left with an empty interpretation. Every postfixed form then shares the entry's full tooltip, so it no longer matters whether the parser read the postfix as part of the key. See Mani and Pcod. Postfixes that name a DISTINCT source stay interpreted; the handful of _ibidem_ citations they strand are marked by hand in wiki.tsv.
NOTE: Concerning authors of works mentioned in Crum's List of Abbreviations, which tend to have short abbreviations (such as 'B' for 'Budge' and 'L' for 'Lemm'), we retain each of their works as separate entries, mimicking the structure of Crum's List of Abbreviations, and affording each work the room it needs to define its own prefixes and postfixes. This also reduces the chances of collision. We do the opposite for authors who are not mentioned in Crum's List of Abbreviations, and who tend to be referred with their last name and initials (such as 'C H Becker' for 'Carl Heinrich Becker'). The author takes a single entry, and each of their works is expressed as a postfix. Such works tend to be cited less often. And the lower frequency and longer abbreviations minimize the chances of collision. These conventions are often broken. Use your judgement.
NOTE: (#668) Some of Crum's citations are too irregular to be recognized automatically, so we label them by hand in wiki.tsv. A postfix commented "Only in manual labels" exists only to serve such labels.
6. FOR DEVELOPERS
